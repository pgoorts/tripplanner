  repository) and `syncStatus` (StateFlow<SyncBarStatus> — IDLE/IN_PROGRESS/FAILED), plus

  `lastSuccessfulSyncAt` write).

Two bugs found and fixed during Step 3.4 device verification:
- Sync bar showed "syncing"/"failed" on plain app/trip open, unrelated to any sync actually in
  progress. Root cause: `OpenedTripViewModel` observed WorkManager's *persisted* state for the
  unique work name `"TripPlannerManualSync"` (`SyncScheduler.observeManualSyncWorkInfo()`), which
  reflects whatever that work name's *last* run (possibly from a prior app session — e.g. a
  previously failed sync, or one left ENQUEUED waiting on connectivity) ended up as. Any new
  screen subscribing to it immediately replayed that stale state. Fixed by having
  `SyncScheduler.triggerManualSync()` return the freshly-built `OneTimeWorkRequest`'s own ID, and
  observing `getWorkInfoByIdFlow(id)` (new `observeSyncWorkInfo(id)`) scoped to that specific
  request instead — the bar now only reflects a sync genuinely happening right now, defaulting to
  IDLE with no eager subscription in `init`.
- Manual sync failed with Firestore `PERMISSION_DENIED` on the trips download query. Root cause:
  `SyncWorker.performDownloadFlow()` built the collaborator-membership query as a dotted string —
  `.whereNotEqualTo("collaborators.$currentUserEmail", null)` — and since email addresses contain
  `.`, Firestore parsed it as nested field segments (`collaborators` → `patrikgoorts@gmail` →
  `com`) instead of the single map key `collaborators["patrikgoorts@gmail.com"]` the security
  rules and upload path actually use. Fixed with
  `FieldPath.of("collaborators", currentUserEmail)`, which treats the email as one literal key.
- Also deployed `firestore.rules` (already existed in the repo root, unrelated to this bug — it
  had just never been pushed) via `firebase deploy --only firestore:rules` after the developer
  created the Cloud Firestore database in the console (Database ID `(default)`, since
  `FirebaseFirestore.getInstance()` is called with no explicit database name anywhere in the
  code); added a `firestore` section to `firebase.json` pointing at it so the CLI picks it up.
  Verified live via the deploy log ("released rules ... to cloud.firestore") and by reading the
  `trips` collection directly with a developer-supplied service-account key (used once for this
  check, then deleted).
Step 3.4 fully verified after these fixes: manual sync now succeeds and round-trips real data to
